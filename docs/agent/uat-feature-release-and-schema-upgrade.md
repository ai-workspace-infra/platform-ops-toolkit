# UAT 特性验收与原地 Schema 升级工作流

本条目记录可复用的交付约束；具体参数以当时的 workflow 和脚本为准。需求、PR、CI、快照 tag、UAT run、人工验收应在 Issue 中互相链接。每完成一个特性只发布一次候选版，等待用户在 UAT 验收，再进入下一特性；不得把“run 绿色”当成人工验收。

## 固定边界

- 默认只做 UAT 部署，不从 PROD 同步数据。PROD→UAT 是独立、显式、一次性的动作；不得把它捆绑到每次发版或 schema 迁移。
- 用户、订阅、付款、用量账本不可物理删除。已有注册用户属性不因迁移被重置；先以只读探针确认现状，再选择兼容旧版数据的增量升级。
- UAT/PROD 凭据不跨环境复用；通过主线工作流的 OIDC→Vault 获取，不能为 PR 分支放宽 Vault 的 `ref`/`job_workflow_ref` 约束，也不能在 dispatch 输入中传 token。
- tag 是不可变交付身份。UAT 只用 `daily-build-*` / `uat-daily-build-*`，重试用新的 `-rN`；不得以 `v*` 标签做 UAT 试验。

## 每个特性的可执行循环

1. **定范围**：Issue 写清目标、受影响仓库、验收断言、不能改变的数据/接口。跨仓 PR 互链，并标明合并顺序。
2. **候选代码**：PR 先跑静态检查、测试和必要的隔离 PostgreSQL 升级/重放测试。数据库变更优先 expand-only；不得依赖重建 public schema 或 `init-schema` 来修复现存 UAT。
3. **发布前检查**：只读探针记录目标库版本、缺失列/约束、脏版本标记；核对每个参与仓库的源 SHA、tag 与制品清单。脚本验证前置状态，不匹配则事务回滚并停止部署。
4. **UAT 发版**：从受信任的 `platform-ops-toolkit@main` 派发完整 `daily-main-snapshot.yaml`；保持 `enable_migration=false`。仅在本次确有已审核 SQL 时显式打开相应 UAT schema 入口；基线采纳和常规增量迁移不可同时开启。当前实现只能用完整主线快照；需要 PR 分支先验收的业务特性应等待下述候选版能力，不能提前合并后再称作“合并前 UAT 验证”。
5. **机器验证**：检查各仓 tag/SHA、CI 制品、serverless 与 selfhost run、DB 迁移版本及脏标记、列/约束、旧行不变性，以及关键 API/页面。失败时保留失败 tag 与证据，修复后生成新 tag；不覆盖旧 tag。
6. **人工闸门**：把 UAT URL、tag、运行记录、迁移前后断言交给用户测试。只有明确验收通过，才关闭相应 Issue、继续下一项。单仓 PR 分支候选版能力上线后，才可把“验收通过→合并该业务 PR”作为强制顺序；当前主线快照模式必须如实记录业务 PR 是否已经合并。平台发布工具修复 PR 与业务特性 PR 分开处理。

## 数据库平滑升级的最小验收

- 升级前：只读确认真实旧结构、`schema_migrations` 状态及关键旧行；缺失的旧字段不能假定存在。
- 升级中：单个事务、向前兼容的 `ADD`/回填策略、明确版本号与 SQL 摘要；禁止隐式生产数据合并或清表。若需 backfill，单独评估锁、批量大小、重放与回滚。
- 升级后：版本号准确且 `dirty=false`，新字段/约束与经核验的索引存在，旧用户属性和账本未改动；第二次执行应无写入或明确拒绝重复采纳。发现旧表缺少可由原迁移 SQL 幂等补建的索引时，先核验全部索引列和表规模，再纳入同一有锁/语句超时的事务。
- 失败：保留日志与快照身份；不通过重跑 `init-schema`、删除行、移动 tag 或放宽认证来“恢复”。

## 待补：单仓 PR 分支候选版

当前 `snapshot_source_ref` 被广播给完整仓库矩阵；填写某一个仓库的 PR 分支会要求其他仓库也存在该分支。`repositories` 缩小为部分仓库时，组合式 UAT 部署被跳过。因此现有入口**不能**兑现“一个 PR 特性分支先部署 UAT，验证后再合并”。

后续应增加受控的、逐仓 source-ref→SHA 覆盖：未指定仓库仍取 `main`，指定仓库只允许同仓 PR 的 head SHA；预检完整矩阵并固定每仓 SHA，形成一个不可变候选 tag，构建/部署仍由 `platform-ops-toolkit@main` 执行，保持现有 Vault 信任边界。还需验证 PR 来源/权限、跨仓兼容、候选版回滚与验收后合并 SHA 的可追溯性。在这项能力交付前，不能用全局 `snapshot_source_ref` 或部分仓库快照假装完成分支 UAT 发布。

## 本轮发现的可复用反例

- 探针发现 `schema_migrations` 不存在、旧版订阅列缺失时，不能直接套用下一版迁移；先做一次受控基线采纳。
- 只检查“表存在、列数正确”不足以证明旧版迁移完整；只读探针应报告索引存在性，并验证建索引所需列。对 UAT 确实缺失的可重放索引，在版本基线写入前幂等补齐。
- 从 PR 分支派发需 Vault 的工作流因 OIDC `ref` 不匹配而失败时，应合并经过审核的平台工作流修复后从 `main` 派发，不扩大 Vault role。
- 数据迁移预览若显示 UAT UUID 更新或 PROD session 插入，就不是“只验证 schema”；须关闭数据迁移输入。源/目标已收敛时，数据迁移应无写入且不产生敏感备份产物。
