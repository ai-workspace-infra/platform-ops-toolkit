# README 动态最新制品仪表盘

本文记录 `ai-workspace-services/.github` 主页和相关 README 的下一阶段目标：
把“按环境自动拉取最新包版本”的展示做成动态版，而不是手工写死当前 tag。

这份文档的角色是设计说明 + 交接说明，不是最终实现代码。它应该让后续 agent
能够直接开始落地，无需再猜数据源、环境分组和展示边界。

## 1. 目标

要做成的不是一个静态表格，而是一个能持续反映最新发布状态的小型仪表盘：

- README 顶部先给出 `sit` / `uat` / `prod` 三张简洁卡片。
- 每张卡片展示该环境的最新发布入口、最新包版本和用途说明。
- 下方的“镜像清单”改成更像仪表盘的卡片布局。
- 每个环境只显示真正属于该环境的最新镜像，避免现在三栏重复显示同一组版本。
- 数据应自动生成，尽量不要手工维护版本号。

## 2. 设计原则

- `sit`、`uat`、`prod` 必须按环境隔离展示，不能共享同一份列表。
- 不能把“包/镜像的存在”当成“该环境最新发布”的充分条件。
- 最新展示必须建立在不可变 tag 或不可变 snapshot 的选择规则上。
- README 本身只负责消费一个已经整理好的数据源，不直接写复杂业务逻辑。
- 如果某个环境当前没有可用最新版本，README 应明确显示空状态，而不是复用别的环境内容。

## 3. 目前已知的输入数据

从前面的快照调试可以确认，后续仪表盘可以从这些信号拼出“最新发布”：

- Git tag 名称，例如 `daily-build-2026.07.29-r4`、`sit-rebuild-2026.07.27-r3`、`prod-release-v2026.07.27`
- tag 对应的 source SHA
- 各服务仓库的 GitHub Packages / GHCR package versions
- 版本标签上的 `latest` / `sha-<commit>` / 环境专用 tag
- 每个 package 的创建时间或版本发布时间
- 必要时从 GitHub Actions run 反查该版本是否确实来自成功构建

## 4. 环境划分建议

### `sit`

- 主要用于验证集成。
- 应展示 `sit-*` 体系下的最新成功快照，或者能映射到 SIT 的最新发布包。
- 如果某些仓库仍只产出 `main` / `latest`，必须先确认这些 tag 是否真的代表 SIT，而不是直接拿来复用。

### `uat`

- 主要用于预发验证。
- 应优先展示 UAT 快照 tag 对应的最新成功镜像。
- 若仓库同时产出 `latest` 和 `sha-*`，README 上要明确哪个是“发布入口”，哪个只是版本定位。

### `prod`

- 主要用于生产发布。
- 只能展示真正经过生产发布链路的版本。
- 不能把 UAT 的 `latest` 误当成生产最新。

## 5. 推荐的数据流

最稳妥的方式不是让 README 自己去实时扫 GitHub API，而是分两层：

1. 生成层
   - 在 `platform-ops-toolkit` 中增加一个生成脚本或 workflow。
   - 该脚本按环境收集各仓库的最新成功包版本。
   - 输出一个可审计的 JSON 或 Markdown 数据文件。

2. 展示层
   - `ai-workspace-services/.github` 主页或对应 README 只引用这份生成好的数据。
   - README 负责排版，脚本负责找数据。

这样做的好处是：

- 生成规则可以在 task 文档里审计。
- README 不会被复杂 shell / API 逻辑污染。
- 后续更换数据源时，只改生成层，不用重写展示层。

## 6. 生成脚本职责

建议后续脚本至少完成这些动作：

- 接收一个环境参数：`sit` / `uat` / `prod`
- 接收一个仓库白名单或映射表
- 为每个仓库找出该环境下最新成功 package 版本
- 输出：
  - 最新 tag
  - 关联 commit
  - 发布时间
  - 对应 package / 镜像名
  - 环境说明
- 如果找不到匹配项，输出明确的空结果，而不是沿用旧值

## 7. README 结构建议

### 顶部

README 顶部放三张卡片：

- `sit`
- `uat`
- `prod`

每张卡片都尽量只保留三类信息：

- 环境名
- 一句用途说明
- 最新发布入口或按钮

### 中部

“镜像清单”使用卡片布局，而不是长表格堆版本号。

每个环境一个区块，每个区块内按服务分卡：

- 服务名
- 最新 tag
- 关联 commit
- 发布时间
- 一句用途说明

### 底部

保留补充说明：

- 数据更新时间
- 数据来源
- 如果某环境没有可用版本，如何处理

## 8. 需要避免的问题

- 三栏重复显示同一组 tag。
- 把 `latest` 当成所有环境通用标签。
- 把“最近创建”误认为“最新成功发布”。
- 仅按 `Published x days ago` 这类 package 页面时间判断最新。
- 把失败构建产生的 package 也当作可展示版本。

## 9. 与快照链路的关系

这条 README 仪表盘线和 `Daily Snapshot` 的关系是：

- 快照链路负责创造不可变 tag 和可追溯的构建基线。
- 仪表盘负责把这些不可变基线按环境展示出来。
- 两者都不应该依赖可移动的 `latest` Git tag。

换句话说，README 应该消费“最新成功快照索引”，而不是自己去猜哪个 tag 是最新。

## 10. 当前可执行的下一步

1. 确认 README 的真实落点是在 `ai-workspace-services/.github` 主页还是服务仓库各自 README。
2. 先定义一份 JSON/Markdown 数据格式，承载每个环境的最新包版本列表。
3. 在 `platform-ops-toolkit` 里实现一个生成脚本，把 GitHub Packages / Actions 数据整理成这份格式。
4. 再把 `ai-workspace-services/.github` 的 README 改成只消费该数据文件。
5. 最后再把 badge、卡片、镜像清单样式做漂亮。

## 11. 交接备注

- 如果后续 agent 继续做 UI，请优先尊重“按环境自动拉取最新包版本”这个原则。
- 如果发现某些仓库只会产出 `latest`，先查构建链路是否已经改成“tag 与 image tag 完全相同”。
- 如果要联动 `Daily Snapshot`，建议直接复用现有不可变快照语义，而不要重新定义一套“最新”的规则。
