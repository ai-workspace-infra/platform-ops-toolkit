# Release status console contract

Toolkit produces `releases.json` on the dedicated `release-status` branch. Portal's authenticated, operations-only GET `/api/operations/releases` proxies that fixed public metadata URL; frontend-router routes it to SSR Console. No browser GitHub credentials, dispatch, or infrastructure mutations are involved.

The catalog retains attempts keyed by workflow run ID and run attempt. A release record identifies environment, immutable tag, scope, workflow URL, timestamps, repository build states, deployment verdict, and verification evidence. UAT acceptance requires the Daily summary job's actual Hybrid dispatch step to succeed; a successful snapshot build alone is never accepted. Serverless emits explicit environment/tag/operation metadata; PROD acceptance requires a full serverless deployment, all required lanes and final verification to succeed. Its scope remains labelled serverless; it does not assert selfhost acceptance. Missing evidence is unknown. Retained historical Serverless dispatch logs can recover only the allowlisted environment, tag, operation, and target fields; ambiguous or expired evidence remains outside coverage.

Daily, weekly (Monday start), and yearly counts are unique successful tags per environment within each Asia/Shanghai period, within reported coverage. Reruns on the same date count once; the same tag successfully redeployed on a different date counts on that date. Latest success uses accepted attempts, independent of later failed retries. Matrix columns are environment/tag pairs and rows are repositories; build and deployment verdicts are separately visible. No record means no evidence, never a fabricated green cell.

A workflow-run collector on the trusted default branch reads allowlisted Actions artifacts and job metadata only. It never executes code from the triggering run, extracts ZIP paths, or publishes logs, secrets, manifests, host configuration or artifact digests. A scheduled refresh and manual backfill repair missed events. A single concurrency group serializes publication; unchanged completed runs are cached, and reads are bounded and parallelized. History persists on the data branch while a 30-day refresh reconciles reruns and available artifacts; gaps and artifact expiry remain visible.

Acceptance: verify deduplication, timezone boundaries, failed retry preservation, absent artifacts, plan exclusion, skipped deployment gates, and cross-repository consolidation; verify BFF authentication/role checks and Worker packaging/routing; compare desktop and narrow layouts with the supplied square-matrix reference; live UAT acceptance requires the merged code's immutable release tag to be deployed and authenticated browser validation.

## Security and synchronization

- Trust only this repository's main runs from schedule/workflow_dispatch and the two named workflow paths. The publisher checks head repository and branch. Checkout is fixed to main with persisted credentials disabled, never to a triggering SHA or artifact code.
- The collector reads Actions evidence. Only its publication job has Contents write permission, and writes only the constant data branch and filename. It has no OIDC, Vault, cloud provider, deployment or dispatch credentials. GitHub's short-lived job token stays on the runner.
- Read a fixed JSON ZIP member with compressed/decompressed size bounds; never extract paths or execute artifact content. Allowlist environment, immutable tag, repository, SHA and status values. Reconstruct workflow links from numeric IDs. Legacy log recovery publishes only four strictly matched fields, never log text. Ambiguous identity fails closed.
- Main branch protections/review remain authoritative for code. Before enabling publication, configure a data-branch ruleset restricting writes to the designated automation identity where the GitHub plan supports it, and document any Actions-token bypass. Browsers get no new write access.
- Serialized publication uses file SHA as a compare-and-swap guard. A conflict fails refresh instead of overwriting concurrent history. Reconcile on completion, every 15 minutes and manual backfill. Cache only inspected completed runs. Preserve accepted attempts after failed reruns. Failed collection does not replace the catalog; display capture time, stale state and missing coverage.
- The Portal proxy requires an account session and existing operations role, uses a fixed HTTPS upstream, validates the catalog and returns private/no-store responses. Inputs cannot control a repository, ref, workflow or upstream URL. There is no dispatch endpoint.

Rollout: merge Toolkit producer; review data-branch protections and backfill; verify the catalog contains only already-public release evidence; merge Router and Portal; issue a fresh immutable UAT tag; verify the Console bundle, authenticated access and displayed quantities. Production infrastructure and IAM permissions remain outside this integration.
